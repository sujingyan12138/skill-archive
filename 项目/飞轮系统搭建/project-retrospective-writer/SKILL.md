# Project Retrospective Writer

## Purpose

把“一次和 AI 完成项目后的聊天成果”稳定落成 `学习/经历/` 中的一篇项目经历。

它适合在项目阶段性完成、告一段落、已经能说清“做成了什么”和“学到了什么”时使用。

## Read First

1. `SOUL.md`
2. `CLAUDE.md`
3. `学习/经历/经历模板.md`
4. `学习/经历/index.md`
5. 先按项目名、仓库名、产品名和核心关键词检索 `学习/经历/`，确认是否已有同项目文件
6. 与当前项目直接相关的材料：
   - 项目仓库中的关键文件
   - 本次对话里产出的关键结论
   - 如有需要，再读 `outputs/`、`wiki/`、`inspection/` 中相关页面

## Output Rules

### A. 经历文

- 目标目录：`学习/经历/`
- 文件名格式：`项目主题与关键历程 YYYY-MM-DD.md`
- 标题格式同文件名，例如 `# KnoBrain 从课程设计原型到个人知识学习工作台阶段成型 2026-05-08`
- 同一项目只保留一个主经历文件；如果 `学习/经历/` 中已经存在同项目经历，不要按新日期另建文件，而是在原文件中新增日期/阶段小节，并同步更新标题、速查或结果部分。
- 不要写成流水账；优先写：
  - 这次要解决什么
  - 中间怎么判断
  - 关键转折是什么
  - 最后怎么做成
  - 踩坑和教训
  - 下次可直接复用的处理顺序
- 尽量链接到仓库内真实文件，而不是空泛描述
- 尽量沿用 `学习/经历/经历模板.md` 的结构，但允许按项目实际情况做增删

### B. 个人感悟边界

- 不根据项目记录自动创建或更新 `生活/复盘/`。
- `生活/复盘/` 只保留用户亲自写下的 `YYYY-MM-DD 今日感悟.md` 和固定的 `复盘.md`。
- 如果用户同时提供了自己的原始感悟并明确要求保存，先完整保留用户原文，再按要求整理；不要把 AI 根据项目推导出的内容伪装成用户感悟。
- 如果用户只想要一份简短的 AI 项目摘要，可另存到 `学习/速看/`，但不要替代完整经历文，也不要写入个人感悟区。

## Writing Priorities

- 优先保留“为什么这样判断”，而不是只写“做了什么”
- 优先提炼可迁移经验，而不是只记录一次性细节
- 优先写让未来的自己一眼能接上工作的内容
- 风格保持真实、具体、可复用，不写空泛鸡汤

## Decision Rules

- 如果这次项目已经形成了稳定方法，可以在经历文中明确写出“下次再遇到时的处理顺序”
- 如果只是一次偶发情绪，不要写进 `SOUL.md`
- 如果这次项目产出了明确系统规则，再考虑补充 `CLAUDE.md`
- 如果内容更像教程或对外表达，另存到 `outputs/`，不要挤进经历文

## Recommended Flow

1. 先读本次项目上下文和仓库里相关文件
2. 判断这次项目最合适的标题和关键历程
3. 先检索 `学习/经历/` 是否已有同项目文件
4. 写入或更新 `学习/经历/` 项目经历；同项目已有文件时追加到原文件
5. 更新 `学习/经历/index.md`，把新经历挂进去，或把旧链接修正到项目主文件
6. 如果这次沉淀了长期可复用的方法，再建议是否补到 `SOUL.md` / `CLAUDE.md`

## Good Trigger Examples

- “请你把这次做项目的经历写进我的 Obsidian 仓库里”
- “帮我把这轮和 AI 协作完成项目的过程沉淀到学习/经历”
- “请把今天这个项目写成经历，保留踩坑和关键转折”
